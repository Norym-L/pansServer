## 互斥锁 std::mutex

关键代码

```cpp
std::mutex mtx; //全局锁

void add_money()
{
	for (int i = 0; i < 1000000; ++i)
	{
		std::lock_guard<std::mutex> lock(mtx);
		++balance;
	}
}
```

原理
- 同一时刻只有一个线程持有锁
- 其他线程阻塞等待，直至锁被释放
- 使用 std::lock_guard 管理锁，离开作用域自动释放（RAII）

代价
- 加锁、解锁有开销，且会导致线程阻塞

## 原子操作

关键代码

```c++
std::atomic<int> balance = 0;  //原子变量

void add_money()
{
	for (int i = 0; i < 1000000; ++i)
	{
		++balance;  //原子自增，硬件保证
	}
}
```

原理
- 对 1、2、4、8 字节的整形，编译器会生成 CPU硬件原子指令（如 lock xadd）
- 读-改-写在硬件层面不可分割，无需加锁
- 性能极高，远快于 mutex

### 线程间关系：互斥vs同步

互斥 = 竞争关系

- 多线程争抢一个独占资源
- 经典场景：多线程同时写一个全局变量

同步 = 合作关系

- 多线程按顺序配合完成一件事
- 经典场景：生产者-消费者模型

### 选型决策树

```
需要保护共享数据？
|- 读多写少 -> std::shared_mutex
|- 临界区极短（几行）？ -> std::atomic
|- 需要同时持有多把锁？ -> std::scoped_lock
|- 默认情况 -> std::mutex + lock_guard
```

### CAS 方案
- CAS 本质：乐观并发----先试，失败重来
- 低竞争下极快，高竞争下可能频繁重试，性能反而不如 mutex

### 测试结论
- 服务器内核里，热点数据（如连接计数， 任务队列）优先考虑 atomic
- 低频共享数据（如配置表）用 mutex 足够，别过度优化
- 性能优化永远先测再改
